# Ninety-Nine Homepage 프로젝트 통합 문서

기준일: 2026-08-10 (Asia/Seoul)

이 파일은 `docs/` 아래의 현재 상태, 아키텍처, 구현 인수인계, QA, 환경 및 후속 작업 문서를 하나로 통합한 단일 기준 문서다. 목표 파일의 완료 조건은 모든 구현·검증 단계 완료 후 배포하는 것이다.

## 1. 목표와 확정 정책

- 센터=매장, 운영자=매장 사장, 직원=매장 직원, 소유자=사이트 소유자.
- 상품·회원 개인정보·출고·보관·배송·매출·정산의 보안 경계는 매장이다.
- 여러 매장 주문은 하나의 결제에 포함될 수 있지만 배송비·배송 요청·송장은 매장 또는 연결된 통합 물류 그룹별로 분리한다.
- 매출은 원판매 매장에 귀속하고 그룹은 그룹 배송비만 정산한다.
- 결제는 소유자가 확인하는 수동 계좌이체만 사용하며 자동 입금확정과 PortOne 실행 경로는 사용하지 않는다.
- 변경은 추가형 migration, RLS, 명시적 GRANT, 매장 범위, 세부 권한, CAS, 멱등 키, append-only 감사 기록을 사용한다.
- 운영 데이터는 관련 없는 주문·환불·배송 이력이 발견되면 변경을 중단한다.

- 핵심 코드·DB·권한·원장·결제·물류·취소·상품·알림·UX·정산·스토리지 변경이 현재 브랜치에 반영되어 있다.
- core test 335개 중 329개 통과, 6개 스킵, 실패 0.
- ESLint, TypeScript, production build 통과.
- Supabase migration parity 157개 일치.
- 운영 BUILD_ID는 현재 배포 커밋과 일치하지만 잔여 작업 완료를 뜻하지 않는다.
- 약관·개인정보 페이지 200, 비인증 cron API 401.
- PortOne·중앙 물류 실행 경로는 폐기하고 역사 읽기만 보존했다.
- 수동 계좌이체, 매장 범위, CAS·멱등·append-only 원장 계약을 유지한다.
- 실제 운영 역할 QA와 결제·환불·배송 mutation은 운영 데이터 보호를 위해 별도 격리 범위로 남겨 두었다.

## 4. 아키텍처·권한 계약

### 역할과 범위

구매자는 일반 구매·입찰·주문·취소·환불을 수행한다. 운영자는 배정된 매장만 관리하며 전역 회원·다른 매장 권한을 변경하지 않는다. 직원은 실제 부여된 `prepare_orders`, `create_shipments` 등 세부 권한만 사용한다. 소유자는 사이트 전역 정책과 명시적으로 선택한 매장 범위의 지원 업무를 수행한다.

### 주문·결제·배송

주문은 하나일 수 있으나 배송 단위는 `store` 또는 `fulfillment_group`이다. 단위마다 상품 목록·배송비·청구 매장·정책 snapshot·배송 요청·송장을 가진다. 결제 원장은 주문 키와 함께 원자적으로 생성하고, 재시도·중복 요청은 멱등 처리한다. 12시간 경과 입금 대기는 구매자의 확인 요청·반복 알림·소유자 에스컬레이션으로 처리하며 자동 확정하지 않는다.

### 취소·정산·스토리지

즉시구매 구매자는 송장 등록 전 취소를 요청할 수 있고, 판매자 무응답은 소유자 확인 대기로 보낸다. 판매자 취소는 구매자 무응답 12시간 후 자동 승인한다. 경매 낙찰자는 취소 요청을 만들 수 없다. 정산은 월·목 오전 9시 기준, 배송비 포함, 일반 5%·프리미엄 3.5%, 10원 단위 올림, 역원장 방식이다. 신규 저장소는 Supabase 우선, R2 조건부, Google Drive 비상용이며 객체 provider/key를 영구 보존한다.

## 5. 검증 증거와 한계

- 역할별 Chrome QA, consolidation verification, DB 테스트 환경 문서는 기준선 증거로 통합했다.
- migration parity, RLS·권한·CAS·멱등·append-only, PortOne·중앙 물류 writer 제거를 검증 대상으로 둔다.
- 브라우저 QA는 인증된 실제 역할 계정으로 추가 확인해야 한다.
- 법률 전문가 검토는 사용자 결정에 따라 현재 범위에서 요구하지 않는다.
- 운영 배포 사실은 BUILD_ID와 도메인 smoke test로 다시 확인해야 하며, 문서만으로 production traffic·환경·데이터 상태를 확정하지 않는다.

## 5-1. 채팅 페이지 무결점 검사 결과

검사 대상: `https://www.ninety-nine-vintage.store/chat`

### 확인된 정상 경계

- 공개 채팅 페이지는 HTTP 200으로 렌더링된다.
- 비인증 `GET /api/chat`와 `GET /api/chat/unread`는 HTTP 401로 차단된다.
- `GET /api/chat/read`는 읽음 변경 전용 POST 경계로 HTTP 405를 반환한다.
- 채팅 core 계약 테스트 7개가 통과했다. 매장별 방 분리, 상품 문의 연결, 직원 배정 범위, 읽음·실시간 알림 계약을 포함한다.
- 브라우저 콘솔 오류·경고는 검사 시점에 발견되지 않았다.

### 확인된 운영 장애 후보

- 인증 세션에서 활성 상담 매장이 0개로 표시되어 `현재 상담 가능한 매장이 없습니다`가 노출되고 상담 입력이 비활성화된다.
- 이것은 프론트 렌더 오류라기보다 활성 매장·운영자 배정·지원 권한 데이터가 비어 있거나 API가 해당 세션에 매장을 반환하지 않는 상황이다.
- 실제 메시지 전송, 재전송, 읽음 처리, 실시간 수신은 상담방이 없는 현재 상태에서 종단간 수행할 수 없으므로 미검증으로 남긴다.

### 채팅 조치 단계

1. **데이터·배정 확인**: 운영 DB read-only로 `stores.is_active`, 운영자 매장 membership, `support_conversations.store_id`, `assigned_staff_id`를 대조하고, 관련 없는 운영 데이터는 변경하지 않는다.
2. **인증·권한 확인**: 일반 회원·운영자·직원 각각의 `/api/chat` 목록 조회와 직접 URL/ID 접근을 확인한다. 자기 매장 외 대화와 internal 대화가 차단되는지 검증한다.
3. **생성·전송 경합 확인**: 동일 매장 상담방 동시 생성, 동일 `clientNonce` 재전송, 중복 클릭, 만료 세션, 401/403/409/503 응답을 격리 테스트 데이터에서 반복한다.
4. **실시간·읽음 확인**: 두 역할의 메시지 수신, 상대 읽음 표시, 채널 timeout/reconnect, 알림 배지와 5초 토스트를 확인한다.
5. **UI 실패 계약 보완**: 활성 매장 0개, 담당자 미배정, API timeout, 전송 실패, 재전송 성공·실패를 각각 구분해 사용자 안내와 복구 버튼을 검증한다.
6. **배포 전후 게이트**: 위 검증 통과 후에만 변경을 커밋하고, 배포 후 `/chat`, `/api/chat` 401, 인증 역할별 smoke test와 rollback 확인을 수행한다.

현재 결론: 공개 접근과 비인증 차단은 정상이나, 상담 가능한 매장 0개 상태 때문에 채팅 업무 흐름은 완료 판정할 수 없다. 데이터 대조와 인증 역할별 종단간 검증이 우선이다.

## 5-2. 피드 페이지 무결점 검사 결과

## 5-3. 즉시 구매(shop) 페이지 무결점 검사 결과

검사 대상: `/shop`, `/m/shop`, 고정가 카드·공유 피드·카트 API·점유 RPC·구매 의도·배송비 견적.

### 확인된 정상 경계

- `/shop`는 HTTP 200, `/m/shop`는 디바이스 라우팅에 따른 307, fixed 상품 API는 HTTP 200으로 응답한다.
- 고정가 상품은 active·published 범위로만 조회되고, 카트 변경은 인증·rate limit·DB RPC를 거친다.
- 카트 점유는 15분·최대 3개·멱등·세션 전환 검증을 유지하며 DB RPC가 최종 권위다.
- 배송비 quote는 charges 구조와 stale 상품을 서버에서 검증한다.
- 비로그인 구매 의도 복원, 고정가 입찰 차단, fixed/auction 카드 UI 분리, canonical SEO 계약이 구현되어 있다.

### 발견된 위험과 우선순위

### shop 조치 단계

1. **기준선 측정**: fixed 상품 수, SSR 응답 크기, 클라이언트 재조회 횟수, 검색어별 결과 일치 여부를 read-only로 측정한다.
2. **SSR 우선 전환**: 초기 상품이 있으면 무조건 전체 재조회하지 않고, 검색 시 서버 `q`를 유지한다. 100개 초과는 `hasMore` 힌트 기반 후속 페이지로 이어받는다.
3. **모바일 payload 통일**: 공용 변환 함수를 만들어 데스크톱·모바일의 필드와 초기 카드 결과를 동일하게 한다.
4. **URL 정책 결정**: `/fixed/{id}` 도입 여부를 결정하고, 유지 시에도 metadata·canonical·구매 CTA가 고정가 의미를 명확히 표현하도록 한다.
5. **카트 오류 UX 보완**: 성공·실패 상태를 분리하고 실패는 `role=alert`와 오류 색상·재시도 안내를 사용한다. 15분 점유 안내는 성공 상태에만 표시한다.
6. **검증·배포 게이트**: 검색·100개 초과·로그인 전환·3개 상한·중복 클릭·만료 점유·배송비 quote·모바일/데스크톱 smoke test 후 배포한다.

현재 결론: P0 결함은 없고 카트·세션·배송비 안전장치는 정상이다. 우선 처리할 구조적 문제는 SH-01의 불필요한 전체 재조회이며, 나머지는 초기 렌더 일관성·URL 의미·실패 안내 개선 과제다.

## 6. 단계별 후속 계획

### 1단계: 계정·홈 정확성

종료·판매완료 찜 복원 계약, 홈 경매 active 필터·상태 라벨·데스크톱/모바일 노출 수 통일, 시드 RNG 주입을 처리한다.

### 2단계: 관리자 UX 정리

운영자 매출·정산 내비게이션과 테스트 계약을 결정하고, 죽은 Operator 콘솔은 참조 테스트 이전 후 삭제 또는 호환 자산으로 명시한다. 소유자 보안 API 4개의 호출 로그·복구 계획을 확인한다.

### 3단계: 공통 구조

데스크톱 배송지 진입점, 간편모드 닉네임, 공통 인증 hook, AccountDashboard 분리, 직원 center redirect 폐기 여부를 처리한다.

### 4단계: 격리 외부 QA

운영자·직원·밴드회원 역할별 실제 도메인 접근을 확인하고, mutation은 격리 테스트 데이터에서만 수행한다.

### 최종 완료·배포 게이트

각 단계의 완료 기준을 통과하고, 배포 전 read-only preflight·커밋·배포·실제 도메인 smoke test·롤백 확인까지 끝난 경우에만 목표를 완료로 표시한다.

## 7. 역사적 결정과 보존 경계

과거 migration, 법적·회계적 이력, 호환 읽기는 삭제하지 않는다. 반면 실행 가능한 PortOne·중앙 물류 writer와 중복된 날짜별 상태 보고서는 현재 기준에서 제외한다. 상세 구현 인수인계와 이전 감사 결과는 이 통합 문서의 정책·검증·후속 계획에 흡수했다.
